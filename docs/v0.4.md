## 1. 项目概述

DDT（弹弹堂）是一款基于 C/S 架构的实时多人回合制弹道射击游戏。玩家在同一张地形图上轮流发射炮弹，考虑风向和角度，击中对手以减少其 HP，率先将对方 HP 降为零者获胜。

项目基于 sylar C++ 协程框架构建服务端，客户端使用 OpenGL 3.3 渲染，通过 WebSocket 进行实时通信。整体分为服务端（gate/lobby/match 三层，物理引擎共享于 `src/common/`）和客户端（逻辑层/渲染层/网络层）两大模块，附带一套基于 Protobuf + ZooKeeper 的 RPC 框架。

### 核心功能

- **回合制弹道射击**：服务端权威物理引擎，客户端插值播放
- **房间系统**：创建/加入/离开/准备/切换队伍，对局结束后返回房间直接开下一局
- **聊天系统**：Team/All/Room/World/System/Broadcast/Private 七频道
- **账号系统**：注册/登录，MySQL 存储 + Redis 会话管理
- **Protobuf 通信协议**：40+ 消息类型，`oneof payload` 多态，支持 import 子 proto
- **RPC 框架**：Protobuf + ZooKeeper 服务注册与发现
- **自动重连**：断线后指数退避自动重连，重连后自动登录恢复状态

## 4. 通信协议

### 4.1 Protobuf 定义

协议定义在 `src/proto/ddt.proto`，通过 `import` 引入子 proto 文件，使用 `oneof payload` 实现多态消息：

```protobuf
message GameMessage {
  oneof payload {
    LoginRequest       login_request       = 1;
    LoginResponse      login_response      = 2;
    JoinRoomRequest    join_room_request   = 3;
    // ... 40+ 消息类型
  }
}
```

子 proto 拆分：`src/proto/{login,room,chat,common}.proto` 各自承载对应域的消息与类型定义，`ddt.proto` 聚合并定义顶层 `GameMessage`。

### 4.2 消息分类

| 类别 | 消息 | 说明 |
|------|------|------|
| **账号** | Login / Register | 登录注册 |
| **房间** | JoinRoom / CreateRoom / RoomList / LeaveRoom / Ready / SwitchTeam | 房间管理 |
| **战斗** | TurnStart / Shoot / ShootResult / Move / GameOver | 回合制战斗 |
| **聊天** | Chat / ChatHistory / PrivateChat | 多频道聊天 |
| **好友** | FriendAdd / FriendList | 好友系统 |
| **通知** | Error / ServerShutdown / OpponentLeft | 系统通知 |

### 4.3 战斗数据流

```
TurnStartNotify (服务端 → 双方)
  ├── turn_player_id: 当前回合玩家
  ├── wind: 风力值
  ├── turn_number: 回合数
  └── 双方完整位置/HP/角度/方向（回合状态校准）

ShootRequest (当前玩家 → 服务端)
  ├── angle: 发射角度（绝对角度，含坡度补偿）
  └── force: 发射力度

ShootResultNotify (服务端 → 双方)
  ├── shooter_id: 射手 ID
  ├── points[]: 弹道轨迹点 (x, y, t)
  ├── hit_x, hit_y: 落点坐标
  ├── hit_player: 是否命中玩家
  ├── damage: 伤害值
  ├── damage_type: NORMAL / CRITICAL / BLOCK
  ├── direction: 发射方向（客户端本地弹道方向转换）
  └── updated_player1/2: 更新后的玩家状态

RoomReadyNotify (服务端 → 双方)
  ├── ... 房间信息
  ├── physics_params: 服务端物理参数下发
  └── max_move_per_turn: 移动限额配置下发
```

## 5. 服务端

### 5.1 分层架构

#### Gate 层（`src/server/gate/`）

- `ddt_main.cc`：服务端入口，初始化 IOManager、数据库、房间管理器，启动 WebSocket 服务器
- `ddt_servlet.h/.cc`：消息路由，已拆分为独立 `handle*()` 方法（按消息类型分发），消除 200 行 switch-case
- `ddt_session_mgr.h/.cc`：Session 生命周期管理，封装 session→player 映射、账号踢人、心跳清理

#### Lobby 层（`src/server/lobby/`）

- `ddt_auth.h/.cc`：账号认证，登录/注册处理，密码加盐哈希，token 生成与验证
- `ddt_chat_manager.h/.cc`：聊天管理，支持 Team/All/Room/World/System/Broadcast/Private 七个频道，聊天记录持久化

#### Match 层（`src/server/match/`）

- `ddt_room_manager.h/.cc`：房间管理，创建/销毁/列表/匹配，`leaveRoom()` 通过 Actor 异步执行确保线程安全
- `ddt_game_room.h/.cc`：单个房间逻辑，Actor 模式串行化房间状态修改，回合状态校准
- `ddt_player.h/.cc`：玩家数据，HP/位置/角度/方向/状态

#### 共享物理层（`src/common/`）

- `ddt_physics.h/.cc`：物理引擎，server 与 client 共用。弹道模拟（重力+风力+空气阻力），地形碰撞检测，伤害计算，坡度角度计算。由 CMake 目标 `ddt_physics_common`（`target_include_directories PUBLIC ${CMAKE_SOURCE_DIR}/src`）暴露，消费者写 `#include "common/ddt_physics.h"` 即可解析。

> 原 `ddt_server/battle/ddt_physics.{h,cc}` 仅是转发 `#include "common/ddt_physics.h"` 的死包装，本次重组已删除，`ddt_game_room.cc` 改为直引 `common/ddt_physics.h`。

#### Config 层（`src/server/config/`，原 `ddt_server/common/`）

- `ddt_config.h/.cc`：配置加载，从 `src/server/conf/game.yml` 读取物理参数、游戏规则、服务器配置。重命名自 `common/` 以避免与共享 `src/common/` 混淆，`config` 更达意。

#### DB 层（`src/server/db/`）

- `ddt_database.h/.cc`：MySQL 连接池，CRUD 操作封装

### 5.2 物理引擎

弹道模拟参数（`src/server/conf/game.yml`），服务端通过 `RoomReadyNotify` 下发给客户端：

```yaml
physics:
  air_factor: 0.89927083
  wind_factor: 5.8709153
  gravity_factor: -172.06527992
  force_factor: 41.0
  dt: 0.01
  max_move_per_turn: 200
```

弹道方程（每帧）：
```
vx *= air_factor
vx += wind * wind_factor * dt
vy += gravity * dt
x  += vx * dt
y  += vy * dt
```

### 5.3 数据库

`src/server/schema.sql` 定义 5 张表：

| 表 | 用途 |
|----|------|
| `accounts` | 账号（用户名、密码哈希、盐） |
| `player_profiles` | 玩家资料（昵称、等级、经验、胜败） |
| `chat_history` | 聊天记录（频道、发送者、内容、时间） |
| `game_records` | 对战记录 |
| `friends` | 好友关系 |

### 6.2 渲染流程

```
Begin(projection)
  ├── 绘制背景（bg_rainbow / bg_ghost）
  ├── 绘制地形（Terrain::Draw）
  ├── 绘制玩家精灵（SpriteBatch::Draw × 2，含坡度旋转）
  ├── 绘制弹道（Projectile::Draw）
  ├── 绘制爆炸效果
  ├── 绘制伤害浮字
  └── 绘制 UI（ImGui）
End()
  └── flush() — 按纹理排序，合并 draw call
```

### 6.4 坐标系统

使用 Y 轴向下的正交投影：

```cpp
glm::ortho(left, right, bottom, top, near, far)
// bottom > top → Y 轴向下
```

## 7. RPC 框架

在 sylar 框架基础上扩展了一套基于 Protobuf + ZooKeeper 的 RPC 框架，位于 `sylar/rpc/`（`rpc_channel.h`、`rpc_provider.h`、`rpc_controller.h`、`zk_client.h`）。

### 7.1 架构

```
Caller (客户端)                          Callee (服务端)
    │                                        │
    │  RpcChannel.CallMethod()               │  RpcProvider
    │  ├── ZK 查找服务地址                    │  ├── notifyService()
    │  ├── 序列化请求                         │  ├── ZK 注册服务
    │  ├── Socket 连接                        │  └── handleClient()
    │  └── 发送/接收                          │      ├── 解析 RpcHeader
    │                                        │      ├── 查找 method
    │  <──── TCP ────>                        │      └── CallMethod()
```

### 7.2 线路协议

```
请求: [4字节 header_size (网络序)][RpcHeader protobuf][args protobuf]
响应: [4字节 response_size (网络序)][response protobuf]
```

### 7.3 ZooKeeper 路径

服务注册路径：`/${service_name}/${method_name}`，节点数据为 `host:port`。

### 7.4 测试

```bash
bash packaging/scripts/build.sh rpc
sudo systemctl start zookeeper
./bin/rpc_test_callee
./bin/rpc_test_caller
```

RPC 测试源码位于 `tests/rpc_test/`（`rpc_callee.cc`、`rpc_caller.cc`、`test.proto`）。

## 10. 实现细节

### 一、核心同步机制：权威服务器 + 表现层客户端

对于弹弹堂这类竞技游戏，防外挂和多端同步是重中之重。

**物理弹道同步方案：**
*   **服务端瞬间推演**：当玩家按下 FIRE 时，服务端 `GameRoom::handleShoot` 调用 `PhysicsEngine::computeTrajectory`。利用带有空气阻力、风力、重力的微积分公式（`AIR_FACTOR`, `WIND_FACTOR`），通过 `dt=0.01` 循环计算完整飞行轨迹点和落点。
*   **客户端插值播放**：服务端将带有时间戳的轨迹点数组通过 Protobuf 下发。客户端 `Projectile::Update` 不进行物理运算，仅根据 `m_elapsedTime` 在两个轨迹点间做线性插值。
*   **评价**：彻底杜绝客户端物理外挂，解决网络抖动导致的位置不同步。

### 二、客户端架构：模块化拆分

原 `game.cc`（1700+ 行 God Class）已拆分为 4 个独立模块：

| 模块 | 文件 | 职责 | 行数 |
|------|------|------|------|
| **GameRenderer** | `src/client/logic/game_renderer.h/.cc` | 世界渲染（地形、人物、弹道、粒子、爆炸、伤害数字、小地图） | 205 |
| **GameNetwork** | `src/client/logic/game_network.h/.cc` | 网络消息解析与游戏状态更新 | 437 |
| **GameHUD** | `src/client/logic/game_hud.h/.cc` | ImGui 面板（HUD、房间列表、聊天、菜单） | 558 |
| **Game** | `src/client/logic/game.cc` | 顶层协调（Init、ProcessInput、Update、updateCamera、Shutdown） | 630 |

各模块通过 `friend class` 访问 Game 的私有成员。

### 三、服务端架构：Actor 模式 + Session 管理

- **SessionManager**：封装 session→player 映射、账号踢人、心跳清理，解耦 Servlet 与 session 管理
- **Actor per Room**：`leaveRoom()` 通过 `post()` 提交到 Actor 队列，所有房间状态修改在 Actor 线程串行执行
- **Servlet handler 拆分**：200 行 switch-case → 独立 `handle*()` 方法，按消息类型分发

### 四、地形破坏：FBO + 延迟像素分配

- 使用 FBO（帧缓冲区对象）实现像素级地形破坏
- `RemoveCircle`：`glReadPixels` 读回 → Alpha 置 0 → `glTexSubImage2D` 传回
- **延迟分配**：`m_pixels`（16MB）不在 Init 预分配，首次 RemoveCircle 时从 GPU 读回
- **地形重建**：`Terrain::Reset()` 方法，新一局开始时重新生成高度图+刷新 GPU 纹理
